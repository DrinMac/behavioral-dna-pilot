# Behavioral DNA Longitudinal Keystroke Study Platform

A deployable FastAPI and PostgreSQL/SQLite system for a one-week online behavioral biometrics study. It provides a guided participant interface and a separate protected researcher console.

## What was retained from the attached prototype

The rebuild preserves and operationalizes the prototype's core research logic:

- real browser `keydown` and `keyup` telemetry;
- eight keystroke metrics;
- baseline mean, standard deviation, behavioral envelope, and shrunk correlation matrix;
- Z-score, Behavioral Envelope, Mahalanobis distance, and Drift engines;
- mean, median, minimum, weighted, and majority fusion;
- Genuine, Monitor, Step-up, and Lock decisions;
- FAR, FRR, accuracy, balanced accuracy, precision, recall, specificity, F1, AUC, EER, and confusion-matrix counts.

## Important redesigns

1. **Longitudinal participant identity** — participants receive `DNA-XXXXX` and a six-digit recovery PIN. A random device token remembers the participant on the same browser.
2. **Separate participant and researcher interfaces** — `/` for participants and `/researcher` for research administration.
3. **One guided participant screen at a time** — no navigation menu; Continue buttons move forward, and Submit is used only after metric review.
4. **Four metric vectors per session** — Initial, Fixed, Free, and Combined. Initial is available from first-time registration; Combined is always Fixed + Free so sessions remain comparable.
5. **Explicit baseline session selection** — each baseline stores the exact selected session database IDs and activity scope.
6. **Holdout protection** — baseline-development sessions cannot be reused as evaluation sessions unless the API's explicit overlap override is deliberately enabled.
7. **Cross-participant impostor testing** — a test session is automatically labeled genuine when it belongs to the baseline participant and impostor otherwise. Researchers can document an explicit override.
8. **Privacy-oriented event storage** — printable key values and exact character codes are not persisted by default. Timing, key categories, corrections, paste events, focus events, and submitted study text are retained.
9. **Portable deployment** — SQLite works locally; PostgreSQL is used by setting `DATABASE_URL` for cloud deployment.
10. **Assisted fixed-text validation** — the reference passage updates while the participant types, highlights the first differing word, reports the expected and entered character, and offers an optional telemetry-safe Pause & Review control.

## Participant flow

1. Study purpose, data collection, privacy, anonymity, and consent
2. Participant registration and autogenerated `DNA-XXXXX`
3. System and device confirmation
4. Fixed-text typing
5. Two free-text prompts
6. Eight-metric result table for Initial, Fixed, Free, and Combined
7. Final Submit
8. Confirmation, progress, Participant ID reminder, and another-session option
9. Automatic return recognition or manual restoration with Participant ID and recovery PIN
10. Repeat until the configured target is reached (default: 10 sessions)

## Researcher flow

1. Password-protected login
2. Dashboard and participant progress
3. Participant/session review and quality details
4. Baseline builder using selected session IDs and metric scope
5. Evaluation setup using selected holdout sessions
6. Four-engine activation, weights, fusion method, and decision thresholds
7. Evaluation results and per-engine confidences
8. ZIP export of participants, devices, sessions, raw events, metric vectors, baselines, evaluation runs, and decisions

## Eight metrics

| Metric | Implementation |
|---|---|
| Hold Time | Matched keyup timestamp minus keydown timestamp |
| Flight Time | Current keydown minus previous keyup (UD); may be negative for overlapping keystrokes |
| Digraph Latency | Current keydown minus previous keydown (DD) |
| Trigraph Latency | Current keydown minus the keydown two strokes earlier (DDD) |
| Typing Speed | Five-character words per minute using summed active field duration |
| Error Rate | Backspace/Delete events divided by printable keystrokes plus corrections |
| Pause Pattern | Mean positive flight time of pauses at least 500 ms; otherwise the 75th percentile |
| Consistency Score | Bounded score derived from hold-time variation and sub-500-ms flight-time variation, with paste penalties |

Timing chains reset between form fields and typing activities, preventing navigation or focus-change gaps from being misclassified as digraphs, trigraphs, or pauses. Fixed-text correction phases also receive separate timing segments when the participant uses **Pause & Review Difference**. Flights of 500 ms or more remain represented by Pause Pattern but are excluded from Consistency Score so the same long pause is not counted twice.

## Fixed-text mismatch assistance

During fixed-text typing, the reference passage is rendered in three states:

- text already matching the participant's entry is shown as correct;
- the first differing reference word or character is highlighted;
- text not yet reached remains pending.

The status line reports the first differing character and what was expected. **Finished Typing** becomes available only when the normalized passage is an exact match. When a participant needs time to inspect an error, **Pause & Review Difference** stops telemetry and disables the typing field. Selecting **Resume Corrections** begins a new timing segment, preventing the review interval from becoming an artificial flight time or consistency penalty.

## Run locally with SQLite

```bash
cd Behavioral_DNA_Study_Deployable
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
export SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')"
export RESEARCHER_PASSWORD="choose-a-strong-password"
uvicorn app.main:app --reload
```

Open:

- Participant interface: `http://127.0.0.1:8000/`
- Researcher console: `http://127.0.0.1:8000/researcher`
- Health check: `http://127.0.0.1:8000/api/health`

The application loads `.env` automatically for local development. Hosting services should configure the same values in their environment-variable dashboard.

## Run locally with PostgreSQL using Docker

```bash
docker compose up --build
```

The participant interface will be available at `http://127.0.0.1:8000/` and the researcher password will initially be `change-me`. Change all secrets before any real data collection.

## Cloud deployment architecture

Recommended one-week pilot architecture:

```text
Participant / Researcher Browser
              |
           HTTPS
              |
     Docker-hosted FastAPI app
              |
       Managed PostgreSQL
```

The included `Dockerfile` works with Docker-capable hosting services. The included `render.yaml` is prepared for a Render web service. Use an external managed PostgreSQL database for durable data.

### Required production environment variables

```text
APP_ENV=production
SECRET_KEY=<long random secret>
RESEARCHER_PASSWORD=<strong unique password>
DATABASE_URL=<PostgreSQL connection string>
TARGET_SESSIONS=10
CONSENT_VERSION=1.0
STUDY_CONTACT=<researcher and institution contact>
STORE_KEY_VALUES=false
```

For PostgreSQL URLs beginning with `postgres://` or `postgresql://`, the application automatically selects the Psycopg 3 driver.

## Suggested session allocation

A reproducible 10-session design could use:

- Sessions 1–6: enrollment/baseline development
- Sessions 7–10: genuine holdout evaluation
- Sessions from other participants: impostor attempts against the selected baseline

The researcher console does not force this split. The exact session IDs are selected and stored, allowing alternative designs such as Sessions 1–7 versus 8–10 or day-stratified selection.

## One-week operating plan

### Before launch

- Finalize the consent wording, institutional approval, data-retention period, and withdrawal process.
- Replace `STUDY_CONTACT` and all secrets.
- Pilot the full process using at least two devices and browsers.
- Confirm that exported CSVs open correctly and that the cloud database remains persistent after an app restart.

### Days 1–6

- Ask participants to complete sessions across different days and times where possible.
- Encourage consistent use of the same keyboard while still recording any equipment change.
- Review progress and quality warnings from the researcher console daily.
- Avoid changing prompts, feature equations, baseline rules, or thresholds after final testing begins.

### Day 7

- Close recruitment or stop accepting new sessions according to the approved protocol.
- Export the complete ZIP dataset.
- Create baseline and holdout selections without overlap.
- Run and save each prespecified engine/fusion configuration.
- Preserve the deployment configuration, source package, export, and analysis notebook as reproducibility evidence.

## Data privacy and security notes

- The participant interface does not request names or emails.
- City and province/state are self-declared; the app does not request browser geolocation.
- The application does not intentionally store IP addresses, but a hosting provider may maintain infrastructure access logs.
- The browser stores only a random participant device token and, on the original browser, the recovery PIN for participant convenience.
- Researcher access uses an HTTP-only signed cookie.
- Production deployment requires HTTPS, a strong researcher password, a strong secret key, and a durable PostgreSQL database.
- Do not collect passwords, confidential account data, exact addresses, or unrelated sensitive free text.

## Automated validation

```bash
pip install -r requirements-dev.txt
PYTHONPATH=. python -m pytest -q
```

The automated tests validate participant registration, remembered sessions, four metric scopes, repeated sessions, assisted fixed-text validation assets, correction-phase timing segmentation, baseline creation, baseline/test separation, four-engine evaluation, expected-label assignment, and dataset export.

## Known research limitations

- Browser timing precision and event delivery can vary by browser, operating system, device load, and privacy settings.
- Keyboard make/model cannot be reliably autodetected and remains self-reported.
- Initial registration telemetry is not repeated on automatically restored sessions; it should not be used as the primary longitudinal baseline scope.
- Ten sessions are suitable for a short pilot but may be insufficient for stable population-level authentication claims.
- Participant-facing metric values are descriptive and should not reveal engine decisions or identity classifications.
